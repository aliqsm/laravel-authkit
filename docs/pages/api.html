API

AuthKit در حالت API، امکانات احراز هویت و مدیریت حساب کاربری را از طریق Endpointهای مستقل در اختیار Frontend قرار می‌دهد. پاسخ این Endpointها به‌صورت JSON است و احراز هویت درخواست‌ها با استفاده از Laravel Sanctum و بر پایه Session و Cookie انجام می‌شود.

در این روش نیازی به تولید و ذخیره Access Token در Frontend نیست. پس از ورود کاربر، مرورگر Cookie نشست را در درخواست‌های بعدی به‌صورت خودکار ارسال می‌کند.

راه‌اندازی API و احراز هویت با Sanctum

۱. فعال‌سازی حالت API

ابتدا در فایل config/authkit.php مقدار app_mode را روی api قرار دهید: 

'app_mode' => 'api',
۲. فعال‌سازی Stateful API

در فایل bootstrap/app.php، متد statefulApi() را به تنظیمات Middleware اضافه کنید: 

->withMiddleware(function (Middleware $middleware): void {
    $middleware->statefulApi();
})

این تنظیم به Sanctum اجازه می‌دهد درخواست‌های ارسالی از دامنه‌های مورد اعتماد Frontend را به‌صورت Stateful پردازش کرده و برای احراز هویت آن‌ها از Session و Cookie استفاده کند.

۳. تنظیم متغیرهای محیطی

در فایل .env مقادیر زیر را متناسب با دامنه‌های پروژه تنظیم کنید: 

SESSION_DRIVER=database
SESSION_DOMAIN=.example.com
SESSION_SECURE_COOKIE=true
SESSION_SAME_SITE=lax

SANCTUM_STATEFUL_DOMAINS=app.example.com
  • SESSION_DRIVER — در این مثال، نشست‌ها در پایگاه داده ذخیره می‌شوند.
  • SESSION_DOMAIN — دامنه‌ای که Cookie نشست برای آن معتبر است.
  • SESSION_SECURE_COOKIE — در صورت فعال بودن، Cookie فقط از طریق HTTPS ارسال می‌شود.
  • SESSION_SAME_SITE — سیاست ارسال Cookie در درخواست‌های بین‌سایتی را مشخص می‌کند.
  • SANCTUM_STATEFUL_DOMAINS — دامنه Frontendهایی که مجاز به استفاده از احراز هویت Stateful هستند. پورت نیز در صورت استفاده باید مشخص شود.

در این مثال، فرض شده Frontend روی app.example.com و API روی api.example.com قرار دارد. تنظیمات Cookie باید با دامنه‌ها و نحوه استقرار پروژه هماهنگ باشند.

۴. تنظیم CORS

ابتدا بررسی کنید فایل config/cors.php در پروژه وجود داشته باشد. اگر این فایل وجود ندارد، می‌توانید تنظیمات پیش‌فرض CORS لاراول را منتشر کنید: 

php artisan config:publish cors

سپس در فایل config/cors.php، دامنه Frontend را در فهرست Originهای مجاز قرار دهید و ارسال Credentialها را فعال کنید: 

'supports_credentials' => true,

'allowed_origins' => [
    'https://app.example.com',
],

فعال بودن supports_credentials برای ارسال و دریافت Cookie در درخواست‌های Cross-Origin ضروری است.

۵. تنظیم Frontend

برای ارسال خودکار Cookieهای Session و CSRF و مدیریت هدر مربوط به آن، تنظیمات Axios را به شکل زیر انجام دهید: 

axios.defaults.baseURL = 'https://api.example.com';
axios.defaults.withCredentials = true;
axios.defaults.withXSRFToken = true;

پیش از ارسال درخواست‌های تغییردهنده وضعیت، مانند ورود و ثبت‌نام، ابتدا Cookie مربوط به CSRF را از لاراول دریافت کنید: 

await axios.get('/sanctum/csrf-cookie');

پس از دریافت Cookie مربوط به CSRF، می‌توانید درخواست ورود را ارسال کنید: 

await axios.post('/api/login', {
    email: 'user@example.com',
    password: 'password',
});

مرورگر در درخواست‌های بعدی، Cookieهای Session و CSRF را به‌صورت خودکار ارسال می‌کند. همچنین Axios با استفاده از تنظیمات بالا، هدر CSRF را مدیریت می‌کند. در صورت منقضی شدن نشست یا بروز خطای CSRF، باید مجدداً Endpoint دریافت Cookie مربوط به CSRF را فراخوانی کنید.

نکته:

برخی قابلیت‌های AuthKit، از جمله ارسال ایمیل‌ها و اعلان‌های امنیتی، از سیستم صف (Queue) لاراول استفاده می‌کنند. برای پردازش این عملیات، باید یک Queue Worker فعال باشد. برای اطلاعات بیشتر به بخش نصب و راه‌اندازی مراجعه کنید.

۱. احراز هویت

در این بخش، Endpointهای مربوط به ورود، ثبت‌نام، خروج از حساب و احراز هویت با حساب گوگل معرفی شده‌اند.

۱. ورود به حساب

برای ورود، ایمیل و رمز عبور کاربر ارسال می‌شوند. در صورت فعال بودن احراز هویت دومرحله‌ای، پاسخ مشخص می‌کند که کاربر باید ابتدا مرحله تأیید دومرحله‌ای را انجام دهد.

Method POST
URL /api/login
Access Guest
Request Body
پارامتر نوع الزامی توضیحات
email string بله ایمیل معتبر، حداکثر ۲۵۵ کاراکتر
password string بله رمز عبور، حداکثر ۲۵۵ کاراکتر
remember boolean خیر فعال‌سازی ورود ماندگار

ایمیل پیش از اعتبارسنجی به حروف کوچک تبدیل و فاصله‌های ابتدا و انتهای آن حذف می‌شود.

مثال
{
    "email": "user@example.com",
    "password": "Password123",
    "remember": true
}
پاسخ موفق (ورود عادی)
{
    "message": "درحال ورود...",
    "data": {
        "next_step": "dashboard"
    }
}
پاسخ موفق (در صورت نیاز به تأیید دومرحله‌ای)
{
    "message": "درحال ورود...",
    "data": {
        "next_step": "two-factor-challenge-form"
    }
}

HTTP Status: 200 OK

خطاهای احتمالی
وضعیت توضیحات
422 ایمیل یا رمز عبور واردشده صحیح نیست.
429 تعداد تلاش‌های ورود از حد مجاز بیشتر شده است.
۲. ثبت‌نام

برای ایجاد حساب کاربری، نام، ایمیل و رمز عبور به همراه تکرار آن ارسال می‌شوند. پس از ثبت‌نام موفق، کاربر باید ایمیل خود را تأیید کند.

Method POST
URL /api/register
Access Guest
Request Body
پارامتر نوع الزامی توضیحات
name string بله نام کاربر، حداقل ۳ و حداکثر ۲۵۵ کاراکتر
email string بله ایمیل معتبر و یکتا
password string بله رمز عبور مطابق قوانین اعتبارسنجی پکیج
password_confirmation string بله تکرار رمز عبور

نام و ایمیل پیش از اعتبارسنجی پاک‌سازی می‌شوند؛ فاصله‌های ابتدا و انتهای آن‌ها حذف شده و ایمیل به حروف کوچک تبدیل می‌شود.

مثال
{
    "name": "Ali",
    "email": "user@example.com",
    "password": "Password123!",
    "password_confirmation": "Password123!"
}
پاسخ موفق
{
    "message": "حساب کاربری شما با موفقیت ایجاد شد",
    "data": {
        "next_step": "email_verification"
    }
}

HTTP Status: 200 OK

۳. ورود و ثبت‌نام با گوگل

AuthKit برای ورود و ثبت‌نام با حساب گوگل از Laravel Socialite استفاده می‌کند. این فرایند در دو مرحله انجام می‌شود:

مرحله اول: هدایت به گوگل
Method GET
URL /api/oauth/google/redirect
Access Guest

این Endpoint کاربر را به صفحه ورود گوگل هدایت می‌کند. نیازی به ارسال پارامتر یا Request Body نیست.

مرحله دوم: بازگشت از گوگل
Method GET
URL /api/oauth/google/callback
Access Guest

این Endpoint نتیجه احراز هویت گوگل را دریافت و کاربر را بر اساس نتیجه به یکی از آدرس‌های تعریف‌شده در تنظیمات authkit.api_urls هدایت می‌کند.

نتیجه مقصد
success oauth_success
two_factor two_factor_challenge
invalid_google_user oauth_failure?error=invalid_google_user
oauth_failed oauth_failure?error=oauth_failed

این دو Endpoint به‌جای پاسخ JSON، از Redirect استفاده می‌کنند.

۴. خروج از حساب

این Endpoint نشست احراز هویت فعلی کاربر را خاتمه می‌دهد.

Method POST
URL /api/logout
Access Authenticated
Request Body

نیازی به ارسال پارامتر یا Request Body نیست.

پاسخ موفق
{
    "message": "خروج از حساب موفقیت‌آمیز بود.",
    "data": {
        "redirect": null
    }
}

HTTP Status: 200 OK

۲. فراموشی و بازیابی رمز عبور

کاربران می‌توانند با استفاده از ایمیل، لینک بازیابی رمز عبور دریافت کنند و از طریق آن رمز عبور جدیدی برای حساب خود تعیین کنند. همچنین کاربران واردشده می‌توانند برای دریافت لینک بازیابی، از ایمیل ثبت‌شده در حساب خود استفاده کنند.

۱. درخواست لینک بازیابی رمز عبور

این Endpoint ایمیل کاربر را دریافت می‌کند و در صورت وجود حساب کاربری، لینک بازیابی رمز عبور را به ایمیل او ارسال می‌کند. برای جلوگیری از افشای وجود یا عدم وجود حساب کاربری، پاسخ در هر دو حالت یکسان است.

Method POST
URL /api/forgot-password
Access Guest
پارامترهای ورودی
پارامتر نوع الزامی توضیحات
email String بله ایمیل معتبر کاربر، حداکثر ۲۵۵ کاراکتر.
مثال
{
    "email": "user@example.com"
}
پاسخ موفق
{
    "message": "اگر حسابی با این ایمیل وجود داشته باشد، لینک بازیابی ارسال خواهد شد."
}

HTTP Status: 200 OK

خطاهای احتمالی
وضعیت توضیحات
429 تعداد درخواست‌های ارسال لینک بازیابی از حد مجاز بیشتر شده است.
500 خطایی هنگام ارسال لینک بازیابی رمز عبور رخ داده است.
۲. بازیابی رمز عبور

این Endpoint توکن بازیابی ارسال‌شده به ایمیل کاربر را به همراه رمز عبور جدید دریافت می‌کند. اعتبار توکن توسط سیستم بازیابی رمز عبور لاراول بررسی می‌شود و در صورت معتبر بودن، رمز عبور حساب به‌روزرسانی خواهد شد.

Method POST
URL /api/reset-password
Access Public
پارامترهای ورودی
پارامتر نوع الزامی توضیحات
email String بله ایمیل معتبر حساب کاربری.
token String بله توکن بازیابی دریافت‌شده از طریق ایمیل.
password String بله رمز عبور جدید، حداکثر ۲۵۵ کاراکتر.
password_confirmation String بله تکرار رمز عبور جدید؛ باید با مقدار password یکسان باشد.
مثال
{
    "email": "user@example.com",
    "token": "reset-token",
    "password": "NewPassword123",
    "password_confirmation": "NewPassword123"
}
پاسخ موفق
{
    "message": "گذرواژه شما با موفقیت تغییر کرد.",
    "data": {
        "password_reset": true
    }
}

HTTP Status: 200 OK

پس از تغییر موفق رمز عبور، توکن Remember کاربر تغییر می‌کند و در صورت فعال بودن قابلیت فعالیت‌های امنیتی، رویداد تغییر رمز عبور ثبت شده و اعلان امنیتی برای کاربر ارسال می‌شود.

خطاهای احتمالی
وضعیت توضیحات
422 ایمیل یا توکن بازیابی معتبر نیست.
500 خطایی هنگام تغییر رمز عبور رخ داده است.
429 تعداد درخواست‌های بازیابی رمز عبور از حد مجاز بیشتر شده است.
۳. ارسال لینک بازیابی برای کاربر واردشده

این Endpoint برای کاربرانی در نظر گرفته شده است که وارد حساب خود شده‌اند و می‌خواهند لینک بازیابی رمز عبور را به ایمیل ثبت‌شده در حسابشان دریافت کنند. در این درخواست نیازی به ارسال ایمیل نیست؛ ایمیل از حساب کاربر احراز هویت‌شده دریافت می‌شود.

Method POST
URL /api/password/send-reset-link
Access Authenticated
پارامترهای ورودی

این Endpoint به پارامتر ورودی نیاز ندارد و ایمیل کاربر از نشست احراز هویت‌شده دریافت می‌شود.

مثال
POST /api/password/send-reset-link
پاسخ موفق
{
    "message": "اگر حسابی با این ایمیل وجود داشته باشد، لینک بازیابی ارسال خواهد شد."
}

HTTP Status: 200 OK

خطاهای احتمالی
وضعیت توضیحات
429 تعداد درخواست‌های ارسال لینک بازیابی از حد مجاز بیشتر شده است.
500 خطایی هنگام ارسال لینک بازیابی رمز عبور رخ داده است.
۴. تأیید رمز عبور

این Endpoint برای تأیید مجدد هویت کاربر پیش از انجام عملیات حساس استفاده می‌شود. رمز عبور فعلی کاربر دریافت و با رمز ذخیره‌شده در حساب او مقایسه می‌شود. در صورت موفقیت، وضعیت تأیید رمز عبور در نشست کاربر ثبت خواهد شد.

Method POST
URL /api/confirm-password
Access Authenticated
پارامترهای ورودی
پارامتر نوع الزامی توضیحات
password String بله رمز عبور فعلی کاربر.
مثال
{
    "password": "CurrentPassword123"
}
پاسخ موفق
{
    "message": "تأیید هویت با موفقیت انجام شد.",
    "data": {
        "password_confirmed": true
    }
}

HTTP Status: 200 OK

۳. تأیید ایمیل

AuthKit امکان بررسی وضعیت تأیید ایمیل، ارسال مجدد لینک تأیید و تأیید آدرس ایمیل از طریق لینک امضاشده را فراهم می‌کند. این قابلیت برای کاربران احراز هویت‌شده در دسترس است؛ لینک تأیید نیز از طریق ایمیل ثبت‌شده در حساب کاربری ارسال می‌شود.

۱. بررسی وضعیت تأیید ایمیل

این Endpoint وضعیت تأیید ایمیل کاربر واردشده را بررسی کرده و نتیجه را در فیلد email_verified برمی‌گرداند.

Method GET
URL /api/email/verify
Access Authenticated
پارامترهای ورودی

این Endpoint به پارامتر ورودی نیاز ندارد.

مثال
GET /api/email/verify
پاسخ موفق

در صورت تأیید بودن ایمیل:

{
    "message": "ایمیل حساب شما قبلاً تأیید شده است.",
    "data": {
        "email_verified": true
    }
}

در صورت تأیید نبودن ایمیل:

{
    "message": "ایمیل حساب شما هنوز تأیید نشده است.",
    "data": {
        "email_verified": false
    }
}

HTTP Status: 200 OK

۲. ارسال مجدد ایمیل تأیید

این Endpoint لینک تأیید ایمیل را مجدداً برای کاربر واردشده ارسال می‌کند. اگر ایمیل کاربر قبلاً تأیید شده باشد، اعلان جدیدی ارسال نمی‌شود.

Method POST
URL /api/email/verification-notification
Access Authenticated
پارامترهای ورودی

این Endpoint به پارامتر ورودی نیاز ندارد و ایمیل کاربر از حساب احراز هویت‌شده دریافت می‌شود.

مثال
POST /api/email/verification-notification
پاسخ موفق
{
    "message": "اگر حساب شما هنوز تأیید نشده باشد، لینک تأیید ارسال می‌شود."
}

HTTP Status: 200 OK

۳. تأیید آدرس ایمیل

این Endpoint از طریق لینکی که به ایمیل کاربر ارسال شده است فراخوانی می‌شود. شناسه کاربر و هش ایمیل در آدرس قرار دارند و اعتبار لینک با استفاده از امضای دیجیتال و اعتبارسنجی درخواست بررسی می‌شود.

Method GET
URL /api/email/verify/{id}/{hash}
Access Authenticated
پارامترهای مسیر
پارامتر نوع الزامی توضیحات
id Integer بله شناسه کاربر.
hash String بله هش آدرس ایمیل کاربر که در لینک تأیید قرار دارد.

این Endpoint به پارامترهای Query جداگانه نیاز ندارد؛ لینک تأیید باید همان لینک امضاشده‌ای باشد که برای کاربر ارسال شده است.

مثال
GET /api/email/verify/1/{hash}?expires={timestamp}&signature={signature}
رفتار پس از تأیید

پس از تأیید ایمیل، کاربر به آدرسی هدایت می‌شود که در گزینه email_verification در بخش api_urls فایل config/authkit.php تنظیم شده است. پارامتر status نیز نتیجه عملیات تأیید را مشخص می‌کند:

مقدار توضیحات
success ایمیل کاربر در این درخواست با موفقیت تأیید شده است.
already ایمیل کاربر پیش از این تأیید شده بوده است.

برای مثال، در صورت تأیید موفق، آدرس مقصد به شکل زیر خواهد بود: 

https://app.example.com/email/verification?status=success

در صورت استفاده از لینک نامعتبر، منقضی‌شده یا متعلق به کاربر دیگر، درخواست توسط اعتبارسنجی لاراول رد می‌شود.

۴. تأیید هویت دومرحله‌ای

AuthKit امکان فعال‌سازی تأیید هویت دومرحله‌ای، ورود با کد یک‌بارمصرف و مدیریت کدهای بازیابی را فراهم می‌کند. برای مدیریت تنظیمات این قابلیت، کاربر باید وارد حساب خود شده و تأیید رمز عبور را انجام داده باشد.

۱. تأیید هویت هنگام ورود
بررسی وضعیت Challenge
Method GET
URL /api/2fa/challenge
Access Guest

این Endpoint وضعیت درخواست تأیید دومرحله‌ای را در Session بررسی می‌کند. در صورت معتبر بودن درخواست، پاسخ زیر برگردانده می‌شود: 

{
    "message": "درخواست تأیید دومرحله‌ای معتبر است.",
    "data": {
        "two_factor_challenge": true
    }
}

در صورت پایان مهلت Challenge، اطلاعات مربوط به آن از Session حذف شده و پاسخ با وضعیت 401 برگردانده می‌شود. 

{
    "message": "مهلت تأیید دومرحله‌ای به پایان رسیده است. لطفاً دوباره وارد حساب خود شوید."
}
تأیید کد دومرحله‌ای
Method POST
URL /api/2fa/challenge
Access Guest

این Endpoint کد واردشده را بررسی می‌کند. کاربر می‌تواند از کد یک‌بارمصرف برنامه احراز هویت یا یکی از کدهای بازیابی استفاده کند.

پارامتر نوع الزامی توضیحات
code string بله کد یک‌بارمصرف یا کد بازیابی

مثال درخواست:

{
    "code": "123456"
}

پاسخ موفق:

{
    "message": "ورود دومرحله‌ای با موفقیت انجام شد.",
    "data": {
        "authenticated": true
    }
}

پس از تأیید موفق، کاربر وارد حساب خود می‌شود و اطلاعات Challenge از Session حذف می‌شوند. در صورت استفاده از کد بازیابی، آن کد نیز از فهرست کدهای قابل استفاده حذف خواهد شد.

خطاهای احتمالی:

وضعیت توضیحات
422 کد واردشده نامعتبر است یا درخواست Challenge اعتبار ندارد یا منقضی شده است.

مهلت اعتبار درخواست Challenge از طریق گزینه challenge_expire_minutes در بخش two_factor فایل config/authkit.php قابل تنظیم است.

۲. مدیریت تأیید هویت دومرحله‌ای

تمام Endpointهای این بخش نیازمند احراز هویت هستند و Middleware مربوط به password.confirm نیز برای آن‌ها اعمال می‌شود.

دریافت وضعیت و اطلاعات راه‌اندازی
Method GET
URL /api/2fa
Access Authenticated

این Endpoint وضعیت تأیید هویت دومرحله‌ای حساب را بررسی می‌کند. اگر این قابلیت فعال نباشد، اطلاعات لازم برای راه‌اندازی، شامل Secret و آدرس QR، در اختیار کاربر قرار می‌گیرد.

نمونه پاسخ در صورت غیرفعال بودن:

{
    "message": "اطلاعات راه‌اندازی تأیید دومرحله‌ای دریافت شد.",
    "data": {
        "enabled": false,
        "secret": "...",
        "qr_url": "otpauth://..."
    }
}

نمونه پاسخ در صورت فعال بودن:

{
    "message": "تأیید هویت دومرحله‌ای فعال است.",
    "data": {
        "enabled": true
    }
}

اطلاعات راه‌اندازی به‌صورت موقت در Session نگهداری می‌شوند و پس از پایان مهلت تعیین‌شده قابل استفاده نخواهند بود.

خطاهای احتمالی:

وضعیت توضیحات
422 فرآیند راه‌اندازی تأیید دومرحله‌ای منقضی شده است.
فعال‌سازی تأیید دومرحله‌ای
Method POST
URL /api/2fa/enable
Access Authenticated

کاربر پس از افزودن حساب خود به برنامه احراز هویت، کد شش‌رقمی تولیدشده را ارسال می‌کند. در صورت معتبر بودن کد، تأیید دومرحله‌ای فعال شده و کدهای بازیابی تولید می‌شوند.

پارامتر نوع الزامی توضیحات
code string بله کد شش‌رقمی برنامه احراز هویت

مثال درخواست:

{
    "code": "123456"
}

پاسخ موفق:

{
    "message": "تأیید هویت دومرحله‌ای با موفقیت فعال شد.",
    "data": {
        "enabled": true,
        "recovery_codes": [
            "ABCD1234...",
            "EFGH5678..."
        ]
    }
}

کدهای بازیابی به‌صورت هش‌شده ذخیره می‌شوند و فقط هنگام تولید در اختیار کاربر قرار می‌گیرند. کاربر باید آن‌ها را در محل امنی نگهداری کند.

خطاهای احتمالی:

وضعیت توضیحات
422 کد واردشده نامعتبر است.
422 تأیید هویت دومرحله‌ای از قبل برای حساب فعال است.
422 مهلت راه‌اندازی تأیید دومرحله‌ای به پایان رسیده است.
غیرفعال‌سازی تأیید دومرحله‌ای
Method POST
URL /api/2fa/disable
Access Authenticated

این Endpoint تأیید دومرحله‌ای را غیرفعال کرده و Secret و کدهای بازیابی ذخیره‌شده را حذف می‌کند. همچنین توکن Remember کاربر تغییر می‌کند و در صورت استفاده از درایور دیتابیس برای Session، نشست‌های دیگر کاربر نیز نامعتبر می‌شوند.

پاسخ موفق:

{
    "message": "تأیید هویت دومرحله‌ای با موفقیت غیرفعال شد.",
    "data": {
        "enabled": false
    }
}

خطاهای احتمالی:

وضعیت توضیحات
403 تأیید هویت دومرحله‌ای برای حساب فعال نیست.
تولید مجدد کدهای بازیابی
Method POST
URL /api/2fa/regenerate
Access Authenticated

این Endpoint مجموعه جدیدی از کدهای بازیابی تولید می‌کند. پس از تولید کدهای جدید، کدهای قبلی دیگر قابل استفاده نخواهند بود.

پاسخ موفق:

{
    "message": "کدهای بازیابی با موفقیت تولید شدند.",
    "data": {
        "recovery_codes": [
            "ABCD1234...",
            "EFGH5678..."
        ]
    }
}

خطاهای احتمالی:

وضعیت توضیحات
403 تأیید هویت دومرحله‌ای برای حساب فعال نیست.
۳. تنظیمات و ملاحظات

مقادیر مربوط به مهلت Challenge، مهلت راه‌اندازی و تعداد و طول کدهای بازیابی از طریق بخش two_factor فایل config/authkit.php قابل تنظیم هستند.

در صورت فعال بودن قابلیت فعالیت‌های امنیتی، رویدادهای مرتبط با فعال‌سازی، غیرفعال‌سازی و مدیریت کدهای بازیابی ثبت شده و اعلان‌های امنیتی مربوطه ارسال می‌شوند.

۵. مدیریت حساب و امنیت

در این بخش، Endpointهای مربوط به مدیریت اطلاعات حساب، تغییر رمز عبور، مشاهده نشست‌های فعال، خروج از سایر نشست‌ها و مشاهده فعالیت‌های امنیتی معرفی شده‌اند.

۱. مدیریت پروفایل

کاربران می‌توانند اطلاعات پروفایل خود را دریافت کرده و نام حساب کاربری خود را ویرایش کنند.

۱. دریافت اطلاعات پروفایل
Method GET
URL /api/profile
Access Authenticated + Verified

اطلاعات کاربر واردشده را در فیلد data.user برمی‌گرداند.

مثال پاسخ:

{
    "data": {
        "user": {
            "id": 1,
            "name": "Ali",
            "email": "user@example.com"
        }
    }
}
۲. ویرایش پروفایل
Method PUT
URL /api/profile
Access Authenticated + Verified

برای ویرایش پروفایل، نام جدید کاربر ارسال می‌شود.

پارامترهای ورودی:

پارامتر نوع الزامی توضیحات
name String بله نام کاربر، حداقل ۳ و حداکثر ۲۵۵ کاراکتر

مثال درخواست:

{
    "name": "Ali Ahmadi"
}

مثال پاسخ:

{
    "message": "اطلاعات حساب با موفقیت به‌روزرسانی شد.",
    "user": {
        "name": "Ali Ahmadi"
    }
}

در صورت نامعتبر بودن اطلاعات ورودی، پاسخ اعتبارسنجی با وضعیت 422 برگردانده می‌شود.

۲. تغییر رمز عبور

کاربران می‌توانند با وارد کردن رمز عبور فعلی و رمز عبور جدید، گذرواژه حساب خود را تغییر دهند.

Method PUT
URL /api/password
Access Authenticated + Verified

پارامترهای ورودی:

پارامتر نوع الزامی توضیحات
current_password String بله رمز عبور فعلی کاربر
new_password String بله رمز عبور جدید؛ حداقل ۸ کاراکتر، شامل حروف کوچک و بزرگ و عدد
new_password_confirmation String بله تکرار رمز عبور جدید برای تأیید

مثال درخواست:

{
    "current_password": "OldPassword123",
    "new_password": "NewPassword123",
    "new_password_confirmation": "NewPassword123"
}

مثال پاسخ موفق:

{
    "message": "رمز عبور با موفقیت تغییر یافت.",
    "data": {
        "password_changed": true
    }
}

پس از تغییر موفق رمز عبور، Remember Token کاربر تغییر می‌کند و در صورت استفاده از درایور دیتابیس برای نشست‌ها، سایر نشست‌های کاربر حذف می‌شوند. همچنین در صورت فعال بودن قابلیت فعالیت‌های امنیتی، اعلان تغییر رمز عبور برای کاربر ارسال می‌شود.

در صورت اشتباه بودن رمز عبور فعلی، نامعتبر بودن رمز عبور جدید یا یکسان بودن رمز جدید با رمز فعلی، خطای اعتبارسنجی با وضعیت 422 برگردانده می‌شود.

۳. مدیریت نشست‌های فعال

کاربران می‌توانند نشست‌های فعال حساب خود را مشاهده کرده و سایر نشست‌ها را از حساب خارج کنند. اطلاعات نشست‌ها از جدول sessions دریافت می‌شود.

۱. دریافت نشست‌های فعال
Method GET
URL /api/sessions
Access Authenticated + Verified

فهرست نشست‌های کاربر را به همراه نوع دستگاه، زمان آخرین فعالیت و وضعیت نشست فعلی برمی‌گرداند.

ساختار اطلاعات هر نشست:

فیلد نوع توضیحات
id String شناسه نشست
device String نوع دستگاه یا سیستم‌عامل شناسایی‌شده
last_activity Integer زمان آخرین فعالیت نشست
isCurrent Boolean مشخص می‌کند نشست مربوط به دستگاه فعلی است یا خیر

مثال پاسخ:

{
    "data": {
        "sessions": [
            {
                "id": "session-id-1",
                "device": "Windows",
                "last_activity": 1794000000,
                "isCurrent": true
            },
            {
                "id": "session-id-2",
                "device": "Android",
                "last_activity": 1793990000,
                "isCurrent": false
            }
        ]
    }
}
۲. خروج از سایر نشست‌ها
Method POST
URL /api/sessions/terminate-others
Access Authenticated + Verified

برای خروج از سایر دستگاه‌ها، کاربر باید رمز عبور فعلی خود را وارد کند. نشست فعلی حفظ می‌شود و سایر نشست‌ها از حساب خارج خواهند شد.

پارامترهای ورودی:

پارامتر نوع الزامی توضیحات
password String بله رمز عبور فعلی کاربر

مثال درخواست:

{
    "password": "CurrentPassword123"
}

مثال پاسخ:

{
    "message": "تمام نشست‌های دیگر با موفقیت خارج شدند.",
    "data": {
        "refresh": true
    }
}

پس از اجرای موفق عملیات، نشست فعلی مجدداً ایجاد می‌شود و مقدار refresh نشان می‌دهد که کلاینت باید وضعیت یا اطلاعات نشست خود را به‌روزرسانی کند.

۴. فعالیت‌های امنیتی

کاربران می‌توانند آخرین رویدادهای امنیتی حساب خود را مشاهده کنند. این اطلاعات از اعلان‌های ثبت‌شده در سیستم لاراول دریافت می‌شوند.

Method GET
URL /api/security-activities
Access Authenticated + Verified

این Endpoint حداکثر ۲۰ فعالیت امنیتی اخیر کاربر را به ترتیب جدیدترین رویداد برمی‌گرداند.

ساختار اطلاعات هر فعالیت:

فیلد نوع توضیحات
id String شناسه اعلان
data Object اطلاعات مربوط به رویداد امنیتی
read_at Date / Null زمان خوانده‌شدن اعلان؛ در صورت خوانده‌نشدن مقدار آن null است
created_at Date زمان ثبت رویداد

مثال پاسخ:

{
    "data": {
        "activities": [
            {
                "id": "notification-id",
                "data": {
                    "event": "password_changed",
                    "ip": "192.0.2.1",
                    "user_agent": "Mozilla/5.0",
                    "time": "2026-11-07T18:00:00.000000Z"
                },
                "read_at": null,
                "created_at": "2026-11-07T18:00:00.000000Z"
            }
        ]
    }
}

نمایش این Endpoint به فعال بودن گزینه security_activities در بخش features فایل تنظیمات AuthKit وابسته است.
